## install.py 重构：移除连通性检查

**起因**：用户执行 `python install.py` 后目标目录 `~/.workbuddy-ai/skills/etf-analysis`
未生成。诊断为 `check_network()` 内的网络异常冒泡到 `main()` 之外，导致

1. 越界 —— 连通性是运行时状态，与"文件是否正确部署"无因果关系

3. 拦不住问题 —— 全绿不代表可用，全红也不代表装不上
4. 反而搞坏主流程 —— 异常直接打断安装
5. 与 SKILL.md 自相矛盾 —— 文档说运行时会自动降级，安装时却强制要求可达

## 收盘后仍请求实时接口 —— 根因：模型自加 `--refresh-live`

**现象**：用户在 21:00 后调用技能，期望走"已收盘复用快照"，但实际仍请求实时
接口并超时报 `Real-time data timed out`，随后走了"重试拉取实时行情"分支。

**排查结论**：脚本无 bug。`is_market_closed()`（`MARKET_CLOSE = 15:05`）逻辑正确，
实测 21:09 运行走 `"via": "复用快照 (已收盘)"`，耗时 0.69s 未走网络。
两处 `fetch_etf.py`（项目 / 已安装）内容一致。

**真正原因**：截图显示模型自主追加了 `--refresh-live`：
```
"$PY" scripts/fetch_etf.py --out "$HOME/etf_out/etf_....json" --refresh-live --save-cache
```
该参数设计上**强制跳过闸门 2、3**（收盘判断 + TTL），故收盘后照样请求接口。

**诱因是文档措辞**：SKILL.md 原文「需要最新价时加 `--refresh-live`」给了模型
"超时 → 需最新价 → 加此参数"的误导路径，反而制造更多超时。

**修正**：
- SKILL.md 新增「⛔ 禁止事项」章节：明令任何情况下不加 `--refresh-live`，
  并给出超时时的正确处理（如实告知用户，不靠参数硬试）
- SKILL.md 失败处理段：把「需要最新价时加 --refresh-live」改为「**不要**加」
- `fetch_etf.py` 的 `--refresh-live` help 文本补充风险警告
- 修复 `--month` help 文案错误：原写"默认上月"，实际 `default_month()` 返回
  **当月**（`datetime.now().strftime("%Y-%m")`）。SKILL.md 早有警告不要设成上月，
  属文档对、help 错

**经验**：收盘闸门是"复用快照"而非"跳过接口"，前置条件是 `last_snap` 存在。
当日首次运行（尚无快照）时必然会请求一次接口，属设计必然行为，不是 bug。

## 【设计修正】收盘后应「跳过」实时接口，而非「复用快照」

用户指出上一轮的修复方向错了：加「禁止 `--refresh-live`」只是约束症状，
真正的毛病是**收盘后根本不该把实时接口当作必要数据源**。

**用户原话要点**：收盘后不需要实时数据，只要完整月度数据即可 —— 月度数据
自然包含当天数据，获取实时数据毫无意义。

**实测验证（关键依据）**：读取 `month_2026-09.json` 三只样本
（SH510010 / SH510020 / SH510030），`series` 最后一条 `trade_date` 均为
**2026-09-21（当天）**，且带当日 `daily_return`。证实收盘后月度数据已含当日行情。

**正确逻辑（按时段区分）**：

| 时段 | 实时接口 | 理由 |
|---|---|---|
| 盘中 (< 15:05) | 必要 | 当日行情还在变，月度数据尚未含今天 |
| 收盘后 (≥ 15:05) | **不必要，直接跳过** | 行情已定格，月度数据已含当日 |

**代码改动**（`fetch_etf.py` 主流程实时数据段整体重写）：
- 引入 `skip_live_due_close = not args.refresh_live and is_market_closed()`
- 收盘后走独立分支：有快照则复用（`via` = `收盘后复用快照 (实时非必要)`），
  无快照则**直接跳过**（`via` = `收盘后跳过 (实时非必要)`，`count=0`）
- 收盘后分支**不再调用 `fetch_live()`**，且 `ok: true` —— 不会因实时缺失而失败
- 三道闸门缩减为盘中两道（`--use-live-cache` / TTL），删掉冗余的收盘判断分支
- 日内快照对比逻辑归入盘中分支

**实测结果**：
- 收盘后有快照：`count=1674`，`via=收盘后复用快照 (实时非必要)`，0.69s 无网络
- 收盘后**无快照**（临时移走快照模拟）：`count=0`，`via=收盘后跳过 (实时非必要)`，
  0.61s，**零网络请求，`ok: true` 不报错** ← 这正是用户要的行为
  （旧逻辑此时会调接口并报 `Real-time data timed out`）

**文档改动**（SKILL.md）：
- 「实时数据的『三道闸门』」章节重写为「实时数据的取舍逻辑 (按时间段区分)」
  + 「盘中的两道复用闸门」
- 明确写下依据：月度 `series` 收盘后最后一条 `trade_date` 就是当天
- 「禁止事项」表述同步更新：强调收盘后**根本不该有实时请求**
- `--refresh-live` help 文案同步

**遗留（未处理）**：非交易日的早上（< 15:05）仍会尝试拉一次实时接口。
因 `is_market_closed()` 只看时间、不判断交易日历。影响有限（失败会自动降级），
若要彻底解决需引入交易日历，改动风险较大，待用户决定。

## 【阈值修正】切换点从 15:05 改为 16:01

用户提供关键实际约束：**月度数据每天 16:00 才完成当日记录落库。**

**这意味着 15:05 是错误阈值**：15:00~16:00 是尴尬窗口 —— 行情已定格，
但月度数据**还没有当天数据**。此时跳过实时接口会**丢失当天记录**。

**修正**：
- 常量改名 `MARKET_CLOSE` → `MONTH_READY = 16:01`
  （16:00 落库 + 1 分钟缓冲，避开落库瞬间边界）
- 函数改名 `is_market_closed()` → `month_data_ready()`
- 语义重新定义：不再是"是否收盘"，而是"**月度数据是否已可替代实时数据**"
- `sources.live.via` 文案同步：`月度已落库, 复用快照 (实时非必要)` /
  `月度已落库, 跳过实时 (实时非必要)`
- warning 文案：`已过 16:00, 月度数据已含当日行情...`

**边界实测**（`month_data_ready()`）：
```
09:30 → False    15:00 → False    15:59 → False
16:00 → False    16:01 → True     21:00 → True
```
15:00~16:00 整个窗口正确保持 `False`（仍需实时数据兜底）。

**文档改动**：SKILL.md 的取舍逻辑表加入 15:00~16:00 子时段说明，
明确写下"月度接口每天 16:00 才写入当日数据"这一关键约束；
README / help 文案 / 代码注释全部同步清理（已 grep 确认无 15:05 残留）。

**三段式时段结论（最终）**：
| 时段 | 实时接口 |
|---|---|
| 盘中 (< 15:00) | 必要（行情在变） |
| 15:00~16:00 | 必要（月度未落库，跳过会丢当天） |
| >= 16:01 | 不必要，直接跳过 |

## 【否决】不加交易日历判断（用户判断正确）

## 修复"卡在思考中"：超时预算 + 进度日志

**用户现象**：WorkBuddy 里显示"思考中"卡了 1m14s，无输出、看不出进展。

**根因（真实缺陷，非环境问题）**：
1. **超时预算被重试翻倍** —— 自动代理回退会试 2 次，
   而 `timeout` 是**每次**的预算，导致总耗时 = timeout × 2 × 接口数。
   最坏：实时 25×2=50s + 走势 30×2=60s + 窗口翻倍 60s = **170s**
2. **全程无任何输出** —— stdout 只在结束时打印 JSON，
   中间几十秒完全静默 → 表现就是"卡死"

**修复**：
- `http_get_json(timeout=N)` 改为**总预算**语义：
  `per_try = max(5, N / len(attempts))`，重试不再翻倍
- 新增 `_note()` → 往 **stderr** 打 `[etf]` 前缀进度（带 flush），
  记录每步：开始采集 / 跳过实时 / 命中缓存 / 请求中（含通路+上限）/
  已响应 HTTP xxx / 通路失败原因 / 采集完成
- 默认超时收敛：实时 25→**12**，走势 30→**20**
- 新增 `label=` 参数给请求打标签（"实时行情"/"走势数据"）

**修复后最坏耗时**：170s → **52s**，且全程可见进度。

**验证**：用不存在的主机跑通了重试路径，确认
`[etf] 测试 请求中 (代理, 第 1/2 次, 上限 5s)` 这类日志正常输出，
总预算 8s 分摊为每次 5s（而非各 8s）。

## 简化 API Key 配置（交互式 + 自动引导）

**用户要求**：让配置更简单。选择方向：**交互式配置** + **自动检测引导**。

### 新的配置方式（从简到繁）

| 方式 | 命令 |
|---|---|
| 交互式（主推） | `python apikey_auth.py` 无参数 |
| 直接传入 | `python apikey_auth.py etf_xxx`（**位置参数**） |
| 环境变量 | `ETF_API_KEY=etf_xxx`（CI / 不落盘） |
| 从采集脚本进入 | `python fetch_etf.py --setup` |

### 关键实现

**1. Key 清洗 `normalize_key()`** — 容忍各种粘贴形态：
- 英文引号 / **中文引号**（中文左右引号是**不同字符**成对，
  不能只比 `s[0]==s[-1]`，必须用 pair 表逐个匹配，这里踩过坑）
- `Bearer ` 前缀、首尾空格、多行内容（只取第一段）

**2. 严格校验 `key_problem()`** — 正则 `^etf_[0-9a-fA-F]{64}$`，
长度不符时明确告知"差多少位"（如"长度是 40, 应为 68 位"），
避免用户对着一个残缺 Key 反复重试。

**3. 剪贴板读取 `read_clipboard()`** — 踩到编码坑：
Windows PowerShell stdout 默认 **GBK/CP936**，用 `text=True` 会抛
`UnicodeDecodeError`。修法：用 bytes 取回再逐编码尝试
（utf-8-sig / utf-8 / gbk / cp936 / latin-1），并在 PowerShell 命令里
加 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。

**4. 自动引导** — `fetch_etf.py` 检测到无 Key 且 `sys.stdin.isatty()` 时
主动询问。**必须判断 isatty**，否则 CI/管道下 `input()` 会抛异常。
提示统一走 **stderr**（与 `_note` 同通道），否则 stdout 缓冲会导致
"先显示开始采集、再要求配置"的顺序错乱。

**5. `--out` 放宽为选填** — 原 `required=True` 使 `--setup` 无法单独运行。
改为 `default=""` + 手动校验（`--setup` 时跳过）。

### 验证
10 种粘贴形态全部通过；环境变量优先级正确；剪贴板读写正常；
`--setup` 转调正常且不触发采集；自动引导顺序正确。

## 【重要修正】交互式输入的前提是错的 + 彻底移除 series 命名

**用户反馈**：`根本没有交互式让我输入key` —— 上一轮"交互式配置"的实际体验是
完全没提示。

### 根因：`sys.stdin.isatty()` 这个前提本身错误

上一轮设计成「isatty 为真才询问」，但**智能体/CI 通过管道调用脚本时 stdin 永远不是 tty**，
所以询问分支**永远不会执行** —— 用户永远看不到交互提示，脚本只是静默打印
"未配置 API Key" 然后继续。这是设计前提错误，不是实现 bug。

**正确的分层**：
1. **首选**：把 Key 直接写在命令里（`apikey_auth.py etf_xxx`）—— 无交互，最可靠
2. **次选**：管道/剪贴板传入（读 piped stdin，读不到再读剪贴板）
3. **兜底**：真的没有 Key 时，打印**可复制的三种配置命令**，而不是假装要交互

**代码改动**：

`apikey_auth.py`
- 新增 `_read_line(prompt)`：返回 `None` 表示 EOF（而非抛异常）
- `interactive_setup()` 重写：非 tty 时**读管道 stdin** → **退回剪贴板** →
  都没有则打印三种配置方式并返回 1
- 输出统一说明"当前不是交互终端，请改用以下任一方式"

`fetch_etf.py`
- 删掉 isatty 守卫的 `input()` 询问
- 改为直接往 stderr 打印可复制的引导，含**绝对路径**的命令（避免 PowerShell 不展开 `~`）

**实测 5 条路径全部正确**：
| 场景 | 结果 |
|---|---|
| 无参数 + 空管道 stdin | 打印三种方式, exit 1 ✅ |
| 无参数 + `echo key \|` 管道 | 保存成功, exit 0 ✅ |
| `--status` | 显示配置来源, exit 0 ✅ |
| `--clear` | 清除成功 ✅ |
| `--status`（清除后） | 提示未配置, exit 1 ✅ |
| 无 Key 跑 `fetch_etf.py` | stderr 引导 + `needs_api_key: true` ✅ |

## 【根因】"收盘了为什么还要采集最新数据" —— 模型措辞 + 一个真 bug

**用户质疑**：连续对话时模型说"我先采集最新数据"，用户反问"都收盘了还能有什么最新数据"。

### 结论 A：脚本行为完全正确，是**模型措辞**误导了用户

实测 22:41（收盘后）连续两次调用，两端 stderr 输出**完全一致**：
```
[etf] 已过 16:01, 走势数据已含当日行情 —— 跳过实时接口 (非必要)
[etf] 走势数据命中缓存 (d15), 不重新拉取
```
`sources` 字段写得明明白白：
- `live.via = 走势已落库, 跳过实时 (实时非必要)` → **根本没请求实时接口**
- `month.via = 缓存 (d15, 未重新拉取)` → **零网络请求**

**所以"采集最新数据"是模型的错误表述**，不是脚本在拉数据。
截图里宿主 App 生成的英文动作标题 "Fetch live quotes and check trend cache"
也在强化这个误导 —— 实际那句 `Fetch live quotes` 根本没发生。

**修复（SKILL.md 新增「⛔ 措辞纪律」章节）**：
要求 agent **先看 `sources.via` 再开口** —— 显示"缓存"就不许说"采集/拉取"；
收盘后不要渲染"最新行情/最新价"，只讲当日涨跌幅与窗口内走势。

### 结论 B：查出一个**真 bug** —— `trend_days` 全部为 None

排查时顺手验证输出，发现 1674 条记录的 `trend_days` **全是 `None`**。

**根因**：合并那行是 `derive_metrics(live, month_rows) if live else month_rows`。
16:01 后 `live` 为空（实时被跳过，属正常路径），于是**直接返回 `month_rows`**，
而这些记录只有 `days` 字段，**没有 `trend_days`**。
下游 `day_counts = sorted(r["trend_days"] ...)` 因 `if r.get("trend_days")` 过滤
而**静默跳过**，所以没报错，只是 `trading_days` 退化成靠 `days` 之外的兜底值。

**性质**：这是**重命名之前就存在的旧缺陷**（当时字段叫 `month_days`，
`month_rows` 里同样没有），我上一轮的 `series`→`trend` 改名只是让它显形。

**修复**（`fetch_etf.py`）：
- 抽出 `_attach_trend_metrics(out, trend)` 统一挂指标，
  **保证 `trend_days` 恒存在**（空序列也写 0）
- `derive_metrics()` 内建"实时为空 → 以走势为主体"分支，逐条补指标；
  顺带 `out.pop("days")` 消除 `days`/`trend_days` 同义字段并存
- 外层合并简化为 `derive_metrics(live, month_rows)`（不再三元判断）

**验证**：收盘后重跑 —— `trend_days None 数量: 0`，中位数 11，
`SH513400` 的 month_return / momentum_5d / volatility / up_day_ratio 全部正常；
回归测试 A(live空)/B(live正常)/C(品种不匹配)/D(score_etfs) 四条分支全通过。

### 经验
"用户看到的" ≠ "实际的"。用户描述"他在采集最新数据"，
**实际是模型用词错误**，脚本一行网络请求都没发。
排查时**先复现实际行为再下结论** —— 这次顺手复现还额外挖出一个静默 bug。
