## install.py 重构：移除连通性检查

**起因**：用户执行 `python install.py` 后目标目录 `~/.workbuddy-ai/skills/etf-analysis`
未生成。诊断为 `check_network()` 内的网络异常冒泡到 `main()` 之外，导致
`[3/4] 数据源连通性` 之后的安装步骤完全没执行（进程静默中断，退出码非 0）。
诱因是本地代理 `http://127.0.0.1:13684` 在 TLS 握手阶段断开连接。

**设计结论**：安装脚本不应检查数据源连通性。理由：
1. 越界 —— 连通性是运行时状态，与"文件是否正确部署"无因果关系
2. 产生虚假失败信号 —— 用户会把网络抖动误读为安装失败
3. 拦不住问题 —— 全绿不代表可用，全红也不代表装不上
4. 反而搞坏主流程 —— 异常直接打断安装
5. 与 SKILL.md 自相矛盾 —— 文档说运行时会自动降级，安装时却强制要求可达

**改动**（`install.py`）：
- 删除 `check_network()` 与 `run_self_test()`
- 新增 `check_required_layout()`（校验 SKILL.md / prompts/prompt_template.md 存在）
- 新增独立命令 `--doctor`：探测连通性，输出 `[WARN]` 而非 `[FAIL]`，**永远返回 0**
- 流程从 4 步压缩为 3 步：环境检查 → 源码检查 → 安装
- 源码检查失败时中止安装（避免装出残缺技能）
- `__main__` 加 `except KeyboardInterrupt` 与通用 `except` 兜底，杜绝静默中断

**改动**（文档）：
- 新建 `ENDPOINTS.md`：集中存放真实接口地址、认证方式、返回结构、Clerk 配置
- `README.md` 「数据源」章节改为指向 `ENDPOINTS.md`，不再出现明文地址
- 新建 `.gitignore`，将 `ENDPOINTS.md` 排除在版本控制外

## 收盘后仍请求实时接口 —— 根因：模型自加 `--refresh-live`

**现象**：用户在 21:00 后调用技能，期望走"已收盘复用快照"，但实际仍请求实时
接口并超时报 `Real-time data timed out`，随后走了"重试拉取实时行情"分支。

**排查结论**：脚本无 bug。`is_market_closed()`（`MARKET_CLOSE = 15:05`）逻辑正确，
实测 21:09 运行走 `"via": "复用快照 (已收盘)"`，耗时 0.69s 未走网络。
两处 `fetch_etf.py`（项目 / 已安装）内容一致。

**真正原因**：截图显示模型自主追加了 `--refresh-live`：
```
"$PY" scripts/fetch_etf.py --out "$HOME/etf_out/etf_....json" --refresh-live --save-cache
```
该参数设计上**强制跳过闸门 2、3**（收盘判断 + TTL），故收盘后照样请求接口。

**诱因是文档措辞**：SKILL.md 原文「需要最新价时加 `--refresh-live`」给了模型
"超时 → 需最新价 → 加此参数"的误导路径，反而制造更多超时。

**修正**：
- SKILL.md 新增「⛔ 禁止事项」章节：明令任何情况下不加 `--refresh-live`，
  并给出超时时的正确处理（如实告知用户，不靠参数硬试）
- SKILL.md 失败处理段：把「需要最新价时加 --refresh-live」改为「**不要**加」
- `fetch_etf.py` 的 `--refresh-live` help 文本补充风险警告
- 修复 `--month` help 文案错误：原写"默认上月"，实际 `default_month()` 返回
  **当月**（`datetime.now().strftime("%Y-%m")`）。SKILL.md 早有警告不要设成上月，
  属文档对、help 错

**经验**：收盘闸门是"复用快照"而非"跳过接口"，前置条件是 `last_snap` 存在。
当日首次运行（尚无快照）时必然会请求一次接口，属设计必然行为，不是 bug。

## 【设计修正】收盘后应「跳过」实时接口，而非「复用快照」

用户指出上一轮的修复方向错了：加「禁止 `--refresh-live`」只是约束症状，
真正的毛病是**收盘后根本不该把实时接口当作必要数据源**。

**用户原话要点**：收盘后不需要实时数据，只要完整月度数据即可 —— 月度数据
自然包含当天数据，获取实时数据毫无意义。

**实测验证（关键依据）**：读取 `month_2026-09.json` 三只样本
（SH510010 / SH510020 / SH510030），`series` 最后一条 `trade_date` 均为
**2026-09-21（当天）**，且带当日 `daily_return`。证实收盘后月度数据已含当日行情。

**正确逻辑（按时段区分）**：

| 时段 | 实时接口 | 理由 |
|---|---|---|
| 盘中 (< 15:05) | 必要 | 当日行情还在变，月度数据尚未含今天 |
| 收盘后 (≥ 15:05) | **不必要，直接跳过** | 行情已定格，月度数据已含当日 |

**代码改动**（`fetch_etf.py` 主流程实时数据段整体重写）：
- 引入 `skip_live_due_close = not args.refresh_live and is_market_closed()`
- 收盘后走独立分支：有快照则复用（`via` = `收盘后复用快照 (实时非必要)`），
  无快照则**直接跳过**（`via` = `收盘后跳过 (实时非必要)`，`count=0`）
- 收盘后分支**不再调用 `fetch_live()`**，且 `ok: true` —— 不会因实时缺失而失败
- 三道闸门缩减为盘中两道（`--use-live-cache` / TTL），删掉冗余的收盘判断分支
- 日内快照对比逻辑归入盘中分支

**实测结果**：
- 收盘后有快照：`count=1674`，`via=收盘后复用快照 (实时非必要)`，0.69s 无网络
- 收盘后**无快照**（临时移走快照模拟）：`count=0`，`via=收盘后跳过 (实时非必要)`，
  0.61s，**零网络请求，`ok: true` 不报错** ← 这正是用户要的行为
  （旧逻辑此时会调接口并报 `Real-time data timed out`）

**文档改动**（SKILL.md）：
- 「实时数据的『三道闸门』」章节重写为「实时数据的取舍逻辑 (按时间段区分)」
  + 「盘中的两道复用闸门」
- 明确写下依据：月度 `series` 收盘后最后一条 `trade_date` 就是当天
- 「禁止事项」表述同步更新：强调收盘后**根本不该有实时请求**
- `--refresh-live` help 文案同步

**遗留（未处理）**：非交易日的早上（< 15:05）仍会尝试拉一次实时接口。
因 `is_market_closed()` 只看时间、不判断交易日历。影响有限（失败会自动降级），
若要彻底解决需引入交易日历，改动风险较大，待用户决定。

## 【阈值修正】切换点从 15:05 改为 16:01

用户提供关键实际约束：**月度数据每天 16:00 才完成当日记录落库。**

**这意味着 15:05 是错误阈值**：15:00~16:00 是尴尬窗口 —— 行情已定格，
但月度数据**还没有当天数据**。此时跳过实时接口会**丢失当天记录**。

**修正**：
- 常量改名 `MARKET_CLOSE` → `MONTH_READY = 16:01`
  （16:00 落库 + 1 分钟缓冲，避开落库瞬间边界）
- 函数改名 `is_market_closed()` → `month_data_ready()`
- 语义重新定义：不再是"是否收盘"，而是"**月度数据是否已可替代实时数据**"
- `sources.live.via` 文案同步：`月度已落库, 复用快照 (实时非必要)` /
  `月度已落库, 跳过实时 (实时非必要)`
- warning 文案：`已过 16:00, 月度数据已含当日行情...`

**边界实测**（`month_data_ready()`）：
```
09:30 → False    15:00 → False    15:59 → False
16:00 → False    16:01 → True     21:00 → True
```
15:00~16:00 整个窗口正确保持 `False`（仍需实时数据兜底）。

**文档改动**：SKILL.md 的取舍逻辑表加入 15:00~16:00 子时段说明，
明确写下"月度接口每天 16:00 才写入当日数据"这一关键约束；
README / help 文案 / 代码注释全部同步清理（已 grep 确认无 15:05 残留）。

**三段式时段结论（最终）**：
| 时段 | 实时接口 |
|---|---|
| 盘中 (< 15:00) | 必要（行情在变） |
| 15:00~16:00 | 必要（月度未落库，跳过会丢当天） |
| >= 16:01 | 不必要，直接跳过 |

## 【否决】不加交易日历判断（用户判断正确）

我提出"补 `weekday()` 挡周末 / 引入交易日历"，被用户驳回，**用户是对的**：

1. **本工具由用户手动调用，不存在定时任务** —— 非交易日通常不会被使用，
   这个场景根本不会发生。我在为不存在的问题设计解决方案。
2. **即便非交易日运行也无害** —— 实时接口返回的是上一交易日静态数据，
   月度数据本就完整。多一次请求不损失信息，也无正确性问题。

**结论：保持现状不改。** `month_data_ready()` 只看时间 = 适度简化，不是缺陷。
引入节假日表需每年维护 + 有跨年失效风险，为一个不存在的收益付出这些成本不划算。
真正值得挡住的浪费场景（16:01 后重复拉取）已由该阈值覆盖。

**文档**：SKILL.md 原注释「不判断周末/节假日」改为明确说明这是**有意取舍而非疏漏**，
写清三点理由，防止后人误判为 bug 又去加日历。

**自身教训**：提出方案前应先确认问题是否真实存在。本例中"手动调用"这一前提
我本该从上下文推断出来（用户全程手动跑命令），却仍按"可能有定时任务"设计。确认前提
比设计方案更重要。
