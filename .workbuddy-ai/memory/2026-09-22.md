## 【三个真 bug】"20 点了为什么还在采集数据"

**用户质疑**：20:00 调用时，模型说"数据采集期间走势接口多次失败，最终通过 curl 直连获取"。
用户反问：都收盘了，为什么还要调接口？

排查后确认 **3 个真实缺陷**，全部已修复。

---

### bug 1（最严重）：缓存字段名变了，但读取时不校验 → 静默退化成空数据

**现象**：`~/.workbuddy-ai/etf-plugin/cache/month_d15.json`（9/22 19:57 写入）
里的记录字段是 **`series`**（旧名），而当前脚本读的是 **`trend`**。

读取时 `r.get("trend")` 直接得到空列表 → 所有 ETF 的走势天数变 0、
动量/波动率全算不出来，但**不报错**，调用方只看到"成功但没数据"。

**根因**：`load_month_cache()` 只判断"文件存在 + rows 非空"，**不校验结构**。
字段改名（`series` → `trend`）没有配套的兼容/失效处理。

**修复**：新增 `_month_rows_look_valid(rows)` —— 至少要有一条记录含 `trend` 字段，
否则**当作未命中**去重新拉取，并打日志 `走势缓存结构已过时 (缺少 trend 字段)`。

**教训**：缓存是跨版本持久化的数据，**改字段名 = 改数据格式**，
必须配套"读取时校验 + 失效重取"，否则旧数据会静默污染新逻辑。

---

### bug 2：`cached_at` 只写不读 → 跨天复用昨天的数据

**现象**：缓存写入时记了 `cached_at`，但**从来没有任何地方读它**。
没有 TTL、没有日期比对 → 昨天存的 `month_d15` 今天会被直接复用。

**后果**：用户拿到**缺当天数据的旧结果**，而且毫无提示。

**修复**：新增 `month_cache_freshness(cached_at)`，按**交易日语义**而非"存了多久"判断：

| 情况 | 判定 |
|---|---|
| 缓存来自别的日期 | 过期（新交易日必然有新数据） |
| 同一天，缓存在 16:01 前生成，而现在已过 16:01 | 过期（16:00 落库了当日行情，缓存里没有） |
| 其余 | 新鲜 |

单测覆盖 5 种情形（含空值、跨天、落库前后），全部正确。

---

### bug 3：`--save-cache` 是选填 → 默认命令永远不写缓存 → 每次都请求接口

**现象**：`save_month_cache()` 被 `if args.save_cache:` 包着，而
**SKILL.md 里推荐的默认命令不带这个参数**（`fetch_etf.py --out out.json`）。
于是每次调用都缓存未命中 → 每次都请求接口 → 接口一抖就失败。

**这就是"走势接口多次失败"的直接原因** —— 不是接口不稳定，是**每次都重打**。

**修复**：改用 `argparse.BooleanOptionalAction`，`--save-cache` **默认开启**，
新增 `--no-save-cache` 关闭。同一天内重复调用直接命中缓存，零请求。

## 附带改进

### 1) 新增 curl 兜底通路（4 条通路自动轮询）

**背景**：实测本机 `https_proxy=http://127.0.0.1:9947`。
同一时刻：urllib 走代理 → SSL EOF；urllib 直连 → 连接被重置；
而 **curl 走代理 → 401（接口可达）**。

**关键认知**：curl 与 urllib 是**两套独立 TLS 栈**（Windows 上 curl 用 Schannel，
urllib 用 OpenSSL），**失败模式不重合**。

**更重要的教训**：哪个能通**并不稳定** —— 昨天的结论是"curl 直连能通、走代理不行"，
今天恰好相反。所以**不能写死任何一种**，必须 2×2 全覆盖：

```
① urllib+代理  →  ② urllib+直连  →  ③ curl+代理  →  ④ curl+直连
```

任一拿到 HTTP 响应即停。实测：urllib 两种模式全失败时，③ curl+代理 成功接管（401）。

> 第一版实现踩坑：把 `_curl_get` 写死 `use_proxy=False`（因为昨天观察到"直连能通"），
> 结果今天直连失败、代理才能通 —— 正是"写死"的代价。已改为两条都试。

**预算**：`fetch_month` timeout 20 → **28s**，`per_try = max(6, 28/4) = 7s`。
最坏 28s（原先 4 条通路若各给满会失控），不会因重试翻倍。

### 2) 接口失败时回退旧缓存（而不是返回空）

拉取失败但存在**结构可用**的旧缓存时，退回使用它，并：
- `sources.month` 标 `stale: true` + `via: 过期缓存 (接口失败回退)`
- 写 warning 要求调用方**告知用户数据可能不含最新交易日**

理由：空数据会让调用方误以为"今天没行情"，而实际只是网络抖动。

### 3) SKILL.md 新增「措辞纪律」（承接昨日）

要求 agent **先看 `sources.via` 再开口**：显示"缓存"就不许说"采集/拉取"。
并明确写入：**发现自己在手工 curl 抓接口 = 脚本通路全挂了，应如实报错，
不要绕过脚本自行取数**（绕过会丢字段结构、写坏缓存 —— 正是 bug 1 的来源）。

## 【补漏】模型绕过脚本手工 curl —— 禁止事项只挡了 `--refresh-live`，没挡"自己动手"

**用户提供 20:00 的完整思考链截图**，暴露了上面三个 bug 之外的另一层问题。

### 截图里的关键推理

```
① 新的持仓来了。我先拉取最新数据——注意缓存是昨天的，需要强制刷新
② 网络通路又出问题了，让我用不同的代理设置重试
③ 三个接口都失败了，让我诊断网络连通性
④ 实时接口通了 (HTTP 200)，走势接口是 000。走势接口比较挑，让我加上 Referer
⑤ 走势接口持续不通，但实时接口正常。我先拿实时数据（含今日涨幅），
   再用昨天的走势缓存补历史      ← 决定性的一句
⑥ 网络在抖。用 curl 重试拉实时行情
⑦ 实时数据拿到了（822KB）。解析持仓数据
```

### 诊断：脚本失败后，模型**整体接管**了取数

- 它没有"绕过脚本调实时接口"，而是**完全弃用脚本**，手工 curl 两个接口
- 实时接口之所以被调，是因为它**用实时数据替代了走势数据**（第 ⑤ 步的推理）
- 它自己加了 `Referer`（猜测性调试），反复换代理设置
- 最终写出的缓存字段是旧的 `series` —— 正是上一节 bug 1 的来源

**关键认知**：`禁止事项` 原文只写了"不要加 `--refresh-live`"，
于是模型找到了合法漏洞 —— **它根本没在用脚本，所以那条禁令管不到它**。
禁令必须覆盖"绕过脚本自行取数"这一整类行为，而不是某个具体参数。

### 修复（三层）

**第 1 层 — 让脚本不再失败（治本）**
上一节的 4 通路兜底 + curl 已解决。脚本自己能成功，模型就没有绕过的动机。

**第 2 层 — 把指令写进模型一定会读的地方**

SKILL.md 的「禁止事项」从 1 条扩为 4 条：
1. 不加 `--refresh-live`（原有）
2. **不手工 curl / 不发任何自行构造的请求**（新增，写明三条危害：
   数据来源不可追溯、写坏缓存、绕过安全闸门）
3. **16:01 后不用实时数据替代走势数据**（新增，说明实时只有当天一个点，
   动量/波动率/上涨天数占比全算不出来），并给出失败时的正确处理优先级表
4. **不猜请求头 / 不反复硬试代理**（新增，针对截图里的 Referer 行为）

`第 1 步 — 采集数据` 开头加「🚩 三条红线」摘要，确保执行前就看到。

**第 3 层 — 把指令注入脚本输出（最关键）**

模型读的是脚本的 JSON 输出。因此在**失败路径的 warnings 里直接写入指令**：

- 回退旧缓存时追加：
  `【请直接使用本结果】不要手工 curl 接口, 也不要用实时数据替代走势数据
   (后者没有历史序列, 动量/波动率/上涨天数占比都无法计算)。`
- 彻底失败时追加：
  `【请勿绕过脚本自行取数】不要手工 curl 接口 —— 手工拼的数据没有 sources 标记、
   字段结构易错 (会写坏缓存), 而且会绕过「16:01 后不请求实时接口」这条安全规则。`

> 设计要点：**指令要放在模型必然会读到的地方**。写在 SKILL.md 里靠自觉，
> 写进它正在解析的 JSON 里才是"贴身提醒"。

### 附带修复

**1) `--refresh-month` 会连回退数据一起丢掉**

原实现 `cached_payload = None if args.refresh_month else load_month_cache(...)` ——
强制刷新时连缓存都不读，于是接口一挂就**空手而归**，连旧数据都用不上。

改为**缓存总是读取**：`--refresh-month` 只影响"是否走命中路径"，
旧缓存始终保留作回退。

**2) 回退旧缓存后不再做"扩大窗口重取"**

原逻辑在数据不足时会 `days*2` 再拉一次 —— 但接口已经全挂，
这等于**再白等一整轮 4×7s=28s**，而且旧缓存本来就"数据不足"，重取也拿不到新数据。

新增 `used_stale_fallback` 标志，为真时跳过该步骤。
实测：全失败场景的日志从 8 次请求降到 4 次。

**3) SKILL.md 新增「不要凭猜测加 `--refresh-month`」**

截图第 ① 步"注意缓存是昨天的，需要强制刷新"就是猜测。
脚本自己会判断跨天/错过落库，不需要人工预判 —— 而且强制刷新会跳过命中路径，白打一次接口。

### 验证
- 全失败 + 昨日缓存 + `--refresh-month`：正确回退，`stale: true`，
  warning 含禁止手工 curl 的指令，**只跑 4 次请求**（修复前 8 次）
- 正常路径：命中缓存，`stale: false`，`trading_days: 12`
- 语法检查通过；项目源码与安装副本 md5 全一致

# 技能备份害 agent 读到了旧 SKILL.md（用户报障，已修根因）

**现象**：agent 直接去翻了**备份的 SKILL.md**，按旧流程干活。

**根因**：备份放在 `~/.workbuddy-ai/skills/` **里面**。该目录下每个含 `SKILL.md`
的子目录都会被当成一个技能加载，所以备份等于注册了第二个（过时的）技能。
`install.py` 的历史演进正好演示了这一点：

1. 最早 → `skills/etf-analysis.bak/`（最糟，是个正常名字，实测确实被 agent 翻到）
2. 我上一轮改成 → `skills/.backup/etf-analysis.<ts>/`（只是加了个点，**仍在 skills/ 里**，没解决问题）
3. 现在 → `~/.workbuddy-ai/skill-backups/etf-analysis.<ts>/`（**移出 skills/**），
   且安装前先清掉旧的，**只保留最近一份**

**清理动作**：
- 删 `skills/.backup/`（2 份完整技能副本，各含 SKILL.md）
- 删新生成的 `skill-backups/`（连这一份也不要，保持"第一次使用"的干净状态）
- 用户明确纠正过一次：说的是**插件（技能）版本的副本**，**不是数据缓存** ——
  所以 `etf-plugin/cache/trend_d15.json` 与 `_cache_backup_*/` **一律没动**
  （当时该主机 4 条通路全挂，缓存是唯一可用数据源）

## 外部 AI 代码评审 → 逐条落实（第 1–6 项）

**① premium_risk 阈值统一（必须修改项）**
Python 里新增唯一定义处 `PREMIUM_MID = 0.5` / `PREMIUM_HIGH = 1.0`，
`score_etfs()` 引用常量；SKILL 只解释 `low` / `mid` / `high` 三个标签，
**不再出现任何阈值数字**（之前 SKILL 写 0.5、Python 写 0.3，两边漂移）。
`smoke_test.py` 加 4b 段：锁定 0.5/1.0 两个常量 + 9 个边界用例（含负值、
含"无 premium_rate 时字段不存在"）。

**② `momentum_5d` → `momentum_5trading_days`**
顺带发现真 bug：原公式 `(cum[-1] - cum[-6]) * 100` 隐含乘了 `(1 + cum[-6])`，
**当窗口前半段涨跌幅大时系统性高估**。实测 1664 只里 **1361 只偏差 > 0.01pp**
（样本 SZ159994：旧 6.7627 vs 正确 6.6099）。
改为对最后 5 个 `daily_return` 逐日累乘。加 4c 段锁定字段名与数值口径。

**③ SKILL 剥离 Python 实现细节**
删掉 curl / TLS / Schannel / OpenSSL / HTTP_PROXY / HTTPS_PROXY / 缓存文件路径 /
snapshot 文件 / TTL / 内部缓存结构 / API 请求细节；CLI 参数只留 4 个可用项，
并注明"代理、缓存、快照、重试由脚本自理，不要手动指定"。

**④ 优先使用 Python 已算好的指标**
SKILL 分析逻辑里加规则：`window_return` / `momentum_5trading_days` /
`volatility` / `up_day_ratio` / `premium_risk` 直接用，不要自己重算。
（榜单排序、筛选不算"重算"，这是取数不是算指标 —— 已在 SKILL 里点明）

**⑤ "必须推荐买入" → "必须给出配置判断"**
输出格式第七段改为配置判断，**允许明确写"暂无明确新增仓位信号"**，
并写明"不得为了满足格式强行推荐"。

**⑥ 禁止 AI 自行扩大 days**
SKILL 规则 3 写死"不自动扩大 days"；Python 里
`trading_days < 10` 的提示语也重写，去掉"建议使用更长周期"这类诱导。
